# Protocol sources — primary-source notes

All facts checked 2026-10-06 against the URLs shown (repo `main`/`master` branches and live docs). `[unverified]` marks claims I could not confirm in a primary source. No design conclusions here.

## 1. MCP (Model Context Protocol)

- Ratified spec revisions: `2024-11-05`, `2025-03-26`, `2025-06-18`, `2025-11-25`, `2026-07-28`, plus `draft` (https://github.com/modelcontextprotocol/modelcontextprotocol/tree/main/docs/specification). Latest is `2026-07-28`; several facts below changed there.
- Wire format is JSON-RPC 2.0; messages MUST be UTF-8 (https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2025-06-18/basic/index.mdx, https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2025-06-18/basic/transports.mdx).
- Tool result content types (https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/schema/2025-06-18/schema.ts): `ContentBlock = TextContent | ImageContent | AudioContent | ResourceLink | EmbeddedResource` (line 1133). `CallToolResult` has `content: ContentBlock[]` and optional `structuredContent?: { [key: string]: unknown }` (lines 819–828).
- `structuredContent` was added in revision **2025-06-18**: "Add support for structured tool output", major change #2, PR #371 (https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2025-06-18/changelog.mdx). It is absent from https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/schema/2025-03-26/schema.ts (grep for `structuredContent` returns nothing).
  - 2025-06-18: "**Structured** content is returned as a JSON object in the `structuredContent` field of a result… a tool that returns structured content SHOULD also return the serialized JSON in a TextContent block" (https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2025-06-18/server/tools.mdx lines 296–300).
  - 2026-07-28 loosens it: "This can be any JSON value (object, array, string, number, boolean, or null)" (https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2026-07-28/server/tools.mdx line 498; changelog minor change #10, SEP-2106).
- Tools may declare an output schema: `outputSchema` is "Optional JSON Schema defining expected output structure"; if provided, "Servers **MUST** provide structured results that conform to this schema" and "Clients **SHOULD** validate structured results against this schema" (tools.mdx 2025-06-18 lines 188, 309–315). 2026-07-28: input/output schemas accept any JSON Schema 2020-12 keywords.
- Content-block annotations (`Annotations`, schema 2025-06-18 lines 1098–1116): optional `audience?: Role[]` (e.g. `["user","assistant"]`) and `priority?: number` 0..1 ("1 means most important"). 2026-07-28 adds "modification times" to the annotation format (tools.mdx 2026 lines 411–415).
- Tool-level `ToolAnnotations` (schema 2025-06-18 lines 881–933): `title`, `readOnlyHint`, `destructiveHint`, `idempotentHint`, `openWorldHint`. Clients "**MUST** consider tool annotations to be untrusted unless they come from trusted servers" (tools.mdx 2025-06-18 lines 191–195).
- Server instructions: `InitializeResult.instructions?: string` — "This can be used by clients to improve the LLM's understanding of available tools, resources, etc. It can be thought of like a 'hint' to the model. For example, this information MAY be added to the system prompt" (schema 2025-06-18 lines 205–212; lifecycle example line 102, https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2025-06-18/basic/lifecycle.mdx). In 2026-07-28 the initialize handshake is removed; `instructions` moves to the required `server/discover` result (https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/schema/2026-07-28/schema.ts `DiscoverResult.instructions` ~lines 683–696; 2026-07-28 changelog major changes #2–3).
- Streamable HTTP (2025-06-18 transports.mdx): server exposes "a single HTTP endpoint path… that supports both POST and GET" (~line 69); each client JSON-RPC message is its own POST (line 84+); `Accept` must list `application/json` and `text/event-stream`; a request POST may be answered with one `application/json` body or an SSE stream; optional GET opens a server→client SSE stream. Optional session: server MAY return `Mcp-Session-Id` on the init response and clients MUST echo it (lines 170–185); SSE resumability via `Last-Event-ID` (lines 152–160). It "replaces the HTTP+SSE transport from protocol version 2024-11-05" (lines 54–58).
- 2026-07-28 transport changes (https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2026-07-28/changelog.mdx; https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2026-07-28/basic/transports/streamable-http.mdx): sessions and `Mcp-Session-Id` removed; stateless requests carry protocol version/capabilities in `_meta`; `initialize`/`notifications/initialized` removed; SSE resumability (`Last-Event-ID`) removed; GET endpoint replaced by `subscriptions/listen`; POST accepts only a single JSON-RPC request or notification (no batching, no client responses); results carry a required `resultType` field.

## 2. Excalidraw format and sync

- `.excalidraw` file is plain JSON: `serializeAsJSON` returns `JSON.stringify(data, null, 2)` with `{type, version, source, elements, appState, files}` (https://github.com/excalidraw/excalidraw/blob/master/packages/excalidraw/data/json.ts); `VERSIONS.excalidraw = 2` (https://github.com/excalidraw/excalidraw/blob/master/packages/common/src/constants.ts lines 419–422). No coordinate quantization during serialization.
- Compression in https://github.com/excalidraw/excalidraw/blob/master/packages/excalidraw/data/encode.ts using `pako`:
  - `encode({text, compress})` → `{version:"1", encoding:"bstring", compressed, encoded}` where compressed bytes are `deflate(text)` as a byte string; `decode` runs `inflate`.
  - `compressData` (encrypted collaboration/file payloads) writes `FileEncodingInfo = {version: 2, compression: "pako@1", encryption: "AES-GCM"}` plus IV, framed by `concatBuffers`: `u32` version, then `u32` length + chunk per buffer.
  - No compression level is passed, so pako defaults apply: `defaultOptions = {level: Z_DEFAULT_COMPRESSION, chunkSize: 16384, windowBits: 15, memLevel: 8, strategy: Z_DEFAULT_STRATEGY, raw: false, gzip: false}` (https://github.com/nodeca/pako/blob/master/src/deflate.ts lines 86–93). `Z_DEFAULT_COMPRESSION = (-1)` (https://www.zlib.net/manual.html). `raw:false` = zlib-wrapped deflate, not raw DEFLATE.
  - `.excalidraw.png`: scene JSON deflated and stored in a PNG `tEXt` chunk keyed `MIME_TYPES.excalidraw`; legacy uncompressed scenes still read (https://github.com/excalidraw/excalidraw/blob/master/packages/excalidraw/data/image.ts `encodePngMetadata`/`decodePngMetadata`, lines 25–71).
- Coordinate precision:
  - `PRECISION = 10e-5` (https://github.com/excalidraw/excalidraw/blob/master/packages/math/src/utils.ts line 1), used as a geometric epsilon (`isCloseTo`), not a serializer rounding step.
  - GitHub code search for `roundToPrecision` across `excalidraw/excalidraw` returns no matches; no general element-coordinate rounding on save found.
  - SVG export quantizes output: `roughSVGDrawWithPrecision` sets roughjs `fixedDecimalPlaceDigits` (https://github.com/excalidraw/excalidraw/blob/master/packages/excalidraw/renderer/staticSvgScene.ts lines 60–73); call sites pass `MAX_DECIMALS_FOR_SVG_EXPORT = 2` (https://github.com/excalidraw/excalidraw/blob/master/packages/common/src/constants.ts; changelog "reducing precision to 2 decimal places", https://github.com/excalidraw/excalidraw/blob/master/packages/excalidraw/CHANGELOG.md PR #3567).
- Freehand/linear elements: `points: readonly LocalPoint[]` (https://github.com/excalidraw/excalidraw/blob/master/packages/element/src/types.ts line 372) and `pressures: readonly number[]` (freedraw, lines 433–434). `LocalPoint = [x: number, y: number] & {_brand}` (https://github.com/excalidraw/excalidraw/blob/master/packages/math/src/types.ts lines 52–54). Points are raw per-point arrays; no delta/quantized encoding in the JSON element model.
- Collaboration (in-repo reference client) uses **socket.io**, not raw WebSocket (https://github.com/excalidraw/excalidraw/blob/master/excalidraw-app/collab/Portal.tsx):
  - Messages are typed `SocketUpdateDataSource` with `SCENE_INIT`, `SCENE_UPDATE` (`payload: {elements}`), `MOUSE_LOCATION`, `IDLE_STATUS`, `USER_VISIBLE_SCENE_BOUNDS` (https://github.com/excalidraw/excalidraw/blob/master/excalidraw-app/data/index.ts).
  - `_broadcastSocketData` JSON-stringifies, UTF-8 encodes, encrypts with the room key (`encryptData`, AES-GCM, IV sent alongside), and `socket.emit("server-broadcast" | "server-volatile-broadcast", roomId, encryptedBuffer, iv)`; server rebroadcasts as `client-broadcast`.
  - Bandwidth limiting: `broadcastScene` sends only elements whose `version` exceeds `broadcastedElementVersions.get(id)` (or when `syncAll`); full resync every `SYNC_FULL_SCENE_INTERVAL_MS = 20000`; deleted elements syncable for `DELETED_ELEMENT_TIMEOUT = 24h` (https://github.com/excalidraw/excalidraw/blob/master/excalidraw-app/app_constants.ts).
- Reconciliation (https://github.com/excalidraw/excalidraw/blob/master/packages/excalidraw/data/reconcile.ts lines 27–42): discard remote element if local is being edited or `local.version > remote.version`, or on equal `version` keep the one with the **lowest `versionNonce`**. Element fields: `version` ("Integer that is sequentially incremented on each change"), `versionNonce` ("Random integer that is regenerated on each change… deterministic reconciliation"), `index` fractional index (types.ts lines 58–69). Received elements are re-versioned via `bumpElementVersions` (https://github.com/excalidraw/excalidraw/blob/master/excalidraw-app/collab/Collab.tsx `_reconcileElements`).

## 3. CRDT sync protocols

### Loro

- Export/import API (https://github.com/loro-dev/loro/blob/main/crates/loro/src/lib.rs): `LoroDoc::export(ExportMode) -> Result<Vec<u8>, LoroEncodeError>` (line 1306); `import(&[u8]) -> Result<ImportStatus, LoroError>` (line 710); `oplog_vv()` (line 887), `state_vv()` (line 893) return `VersionVector`.
- `ExportMode` (https://github.com/loro-dev/loro/blob/main/crates/loro-internal/src/encoding.rs lines 53–71): `Snapshot` (full history + current state), `Updates {from: VersionVector}` ("history since the `from` version vector"), `UpdatesInRange {spans}`, `ShallowSnapshot(frontiers)`, `StateOnly`, `SnapshotAt`; `all_updates()` = `Updates` from an empty VV (lines 93–98).
- Import guidance: check `ImportStatus.pending`; if non-empty "fetch those missing ranges (e.g., using `export(ExportMode::updates(&doc.oplog_vv()))`) and re-import" (lib.rs lines 705–708).
- Wire format (https://github.com/loro-dev/loro/blob/main/docs/encoding.md): current snapshot mode `3` (`FastSnapshot`), incremental updates mode `4` (`FastUpdates`). Mode 4 is "a concatenation with no block count and no terminator: `repeat until EOF: uleb block_len; u8 postcard_change_block[block_len]`" (§6); mode 4 blocks are never LZ4-compressed and have no per-block checksum. Mode 3 has three length-prefixed sections, KV/SSTable storage; blocks may be LZ4 frames, kept only if not strictly larger than raw (https://github.com/loro-dev/loro/blob/main/docs/encoding-lz4.md §1).
- Version vectors: postcard `FxHashMap<PeerID, Counter>` with **exclusive** counters, order not canonical; frontiers = sorted postcard `Vec<ID>` (encoding.md §5.2–5.3; "In code, it has exclusive end", https://github.com/loro-dev/loro/blob/main/docs/Glossary.md line 20). Default block split target 4 KiB (encoding.md §6); SSTable block checksum xxHash32 seed `0x4f524f4c`.
- No overhead/size ratios found in these docs — only format constants. `[unverified: documented overhead or size characteristics]`.

### Automerge

- Sync protocol docs (https://github.com/automerge/automerge/blob/main/rust/automerge/src/sync.rs lines 1–30): based on arXiv:2012.00472, assumes "a reliable in-order stream between two peers"; each peer keeps a `State` and alternates `generate_sync_message()` / `receive_sync_message()` until neither has data.
- Sync `Message` (sync.rs lines 528–547): `heads: Vec<ChangeHash>`, `need: Vec<ChangeHash>`, `have: Vec<Have>`, `changes: ChunkList` (bytes for `load_incremental`), `flags`, `version`. Type bytes: V1 `0x42`, V2 `0x43` (lines 136–163); V2 packs changes into one length-delimited chunk (comment lines 521–527).
- `Have` (https://github.com/automerge/automerge/blob/main/rust/automerge/src/sync/state.rs lines 80–90) = `{last_sync: Vec<ChangeHash>, bloom: BloomFilter}`; bloom filter = "a summary of the changes that the sender… has added since the last sync", implicitly requesting what's missing.
- Bloom filter: `BITS_PER_ENTRY = 10; NUM_PROBES = 7;` — "correspond to a 1% false positive rate. The values can be changed without breaking compatibility… since the parameters… are encoded in the wire format" (https://github.com/automerge/automerge/blob/main/rust/automerge/src/sync/bloom.rs lines 7–10).
- Document/change compression: `DEFLATE_MIN_SIZE: usize = 256` (https://github.com/automerge/automerge/blob/main/rust/automerge/src/storage/change.rs line 17); `compress()` returns `Some` only when `bytes.len() > DEFLATE_MIN_SIZE` (lines 295–301). Compressed chunks read with `flate2::bufread::DeflateDecoder` (https://github.com/automerge/automerge/blob/main/rust/automerge/src/storage/chunk.rs lines 80–86). README (https://github.com/automerge/automerge/blob/main/README.md line 11): "a compact compression format… and a sync protocol" — no size figures. `[unverified: document format sizes]`.

### Yjs

- Updates: "encoded into binary encoded (highly compressed) *document updates*… *commutative, associative,* and *idempotent*" (https://docs.yjs.dev/api/document-updates). API: `Y.encodeStateAsUpdate(doc[, targetStateVector])`, `Y.encodeStateVector(doc)`, `Y.applyUpdate`, incremental `ydoc.on('update', …)`, plus `Y.mergeUpdates` / `Y.diffUpdate` that work on encoded updates without loading a `Y.Doc`.
- The no-doc path "only merges document updates and doesn't garbage-collect deleted content. You still need to load the document to a Y.Doc to reduce the document size" (same page).
- State vectors: "A state vector defines the known state of each user (a set of tuples `(client, clock)`). This object is also efficiently encoded as a Uint8Array." Sync = send state vector ("sync step 1"), remote computes a minimal missing-update message ("sync step 2") (https://github.com/yjs/yjs/blob/main/INTERNALS.md lines 153–163).
- GC: "when an object is deleted its content is discarded… replaced with a `GC` object (*src/structs/GC.js*). This is a very lightweight structure - it only stores the length of the removed content" (INTERNALS.md lines 112–116).
- Encoding: lib0 varints — `writeVarUint` writes 7-bit groups, 8th bit = continuation, least-significant group first (https://github.com/dmonad/lib0/blob/master/encoding.js lines 243–249); `writeVarUint8Array` writes `varint(byteLength)` then bytes (341–344); `writeVarInt` "use the 7th bit… for signaling that this is a negative number" (comment lines 256–259).

## 4. WebSocket compression on the wire

- RFC 7692 defines "permessage-deflate": compress each message payload with DEFLATE (RFC 1951) using RFC 1979 byte alignment; "The DEFLATE algorithm is widely available on various platforms, and its overhead is small" (https://www.rfc-editor.org/rfc/rfc7692.html §1). Negotiated via `Sec-WebSocket-Extensions` offer/response; parameters `server_no_context_takeover`, `client_no_context_takeover`, `server_max_window_bits`, `client_max_window_bits` (§7.1); simplest header `Sec-WebSocket-Extensions: permessage-deflate` (§7.1.3).
- Compression procedure (§7.2.1): DEFLATE the payload, append an empty DEFLATE block if needed, then "Remove 4 octets (that are 0x00 0x00 0xff 0xff) from the tail end"; the receiver appends them back before inflating. `[unverified: typical effect on JSON payloads — the RFC states no sizes or ratios]`.
- Browsers: the WHATWG WebSockets Standard has the UA append a user-agent-defined header — "Let permessageDeflate be a user-agent defined `permessage-deflate` extension header value… `permessage-deflate; client_max_window_bits`" — as `Sec-WebSocket-Extensions` (https://websockets.spec.whatwg.org/#websocket-opening-handshake steps 9–10). Scripts cannot configure it; `extensions` is read-only — "returns the extensions selected by the server. This is currently only the empty string or a list of extensions as negotiated by the connection" (https://developer.mozilla.org/en-US/docs/Web/API/WebSocket/extensions).
- Rust — **no permessage-deflate**: tungstenite README (master, checked 2026-10-06): "There is no support for permessage-deflate at the moment, but the PRs are welcome" (https://github.com/snapview/tungstenite-rs/blob/master/README.md); crates.io latest 0.30.0; features `handshake`, `url`, TLS only — no deflate (https://github.com/snapview/tungstenite-rs/blob/master/Cargo.toml). `tokio-tungstenite` 0.30.0 features: `connect`, `handshake`, `stream`, TLS only (https://github.com/snapview/tokio-tungstenite/blob/master/Cargo.toml). axum 0.8.9 `axum/src/extract/ws.rs` (https://github.com/tokio-rs/axum/blob/main/axum/src/extract/ws.rs) contains no `Sec-WebSocket-Extensions`/deflate handling (only `Sec-WebSocket-Protocol`); ws dependency = `tokio-tungstenite` 0.29 (https://github.com/tokio-rs/axum/blob/main/axum/Cargo.toml line 141). `[unverified: any axum/tokio-tungstenite fork or future version that adds it]`.
- Browser app-level decompression: `DecompressionStream(format)` accepts `"brotli"`, `"gzip"`, `"deflate"`, `"deflate-raw"` and `"zstd"` (https://developer.mozilla.org/en-US/docs/Web/API/DecompressionStream/DecompressionStream, page last modified 2026-06-22). Support for the newer formats varies by browser; check the MDN compatibility table before relying on zstd/brotli.
- RFC 6455 binary vs text: same base framing; opcode `%x1` = text, `%x2` = binary (https://www.rfc-editor.org/rfc/rfc6455.html §5.2). Text: "The 'Payload data' is text data encoded as UTF-8… the whole message MUST contain valid UTF-8"; Binary: "arbitrary binary data whose interpretation is solely up to the application layer" (§5.6). Clients MUST mask frames; servers MUST NOT (§5.3). WHATWG `send()` maps strings to text frames, Blob/ArrayBuffer(View) to binary frames (WebSockets Standard §3.1).

## 5. Compact serialization formats

- CBOR (RFC 8949): preferred serialization "always uses the shortest form of representing the argument" and "the shortest floating-point encoding that preserves the value" (§4.1, https://www.rfc-editor.org/rfc/rfc8949.html); deterministic encoding = preferred serialization MUST be used (§4.2.1). Appendix A examples: `0`=`0x00`, `23`=`0x17`, `24`=`0x1818`, `1000`=`0x1903e8`; half/single/double float markers `0xf9`/`0xfa`/`0xfb`.
- MessagePack (https://github.com/msgpack/msgpack/blob/master/spec.md): single-byte type tags — `positive fixint` 0x00–0x7f, `fixmap` 0x80–0x8f, `fixarray` 0x90–0x9f, `fixstr` 0xa0–0xbf (§Formats Overview). `float 32` 0xca, `float 64` 0xcb; type system: "Float represents a IEEE 754 double precision floating point number" (line 55). No size-benchmark numbers vs JSON in the spec. `[unverified: compact small-example size numbers in the spec]`.
- JSON numbers: RFC 8259 §6 (https://www.rfc-editor.org/rfc/rfc8259.html): "This specification allows implementations to set limits on the range and precision of numbers accepted. Since software that implements IEEE 754 binary64 (double precision) numbers … is generally available and widely used, good interoperability can be achieved by implementations that expect no more precision or range than these provide"; integers in `[-(2**53)+1, (2**53)-1]` interoperate exactly. One `number` production — no integer/float distinction.
- ECMAScript: "The Number type has exactly … values, representing the double-precision floating point IEEE 754-2019 binary64 values" (https://tc39.es/ecma262/multipage/ecmascript-data-types-and-values.html#sec-ecmascript-language-types-number-type). JSON parsed in JS cannot preserve 64-bit integers beyond 2^53.
- Float quantization in real systems:
  - Google Encoded Polyline Algorithm: lossy; multiply each coordinate by 1e5 and round; store offsets from the previous point; 5-bit chunks; +63 to ASCII; example `(38.5,-120.2),(40.7,-120.95),(43.252,-126.453)` → ``_p~iF~ps|U_ulLnnqC_mqNvxq`@`` (https://developers.google.com/maps/documentation/utilities/polylinealgorithm).
  - Mapbox Vector Tile spec 2.1 §4.3: "Coordinates within a geometry MUST be integers." 32-bit ints: `CommandInteger = (id & 0x7) | (count << 3)` (MoveTo id 1, LineTo id 2, ClosePath id 7); parameters zigzag `ParameterInteger = (value << 1) ^ (value >> 31)`, deltas from a cursor (`pX = cX + dX`) (https://github.com/mapbox/vector-tile-spec/blob/master/2.1/README.md §4.3.1–4.3.3).

## 6. Token-efficient structured formats for LLMs

- TOON (https://github.com/toon-format/toon): "a compact, human-readable encoding of the JSON data model"; indentation for nested objects + CSV-style tabular rows for uniform data. README claims `42.6% fewer tokens` than JSON at comparable accuracy (`72.2%` vs `71.4%`) and a weather example "~117 tokens [JSON] against TOON's ~66". It also documents JSON wins: mixed-structure total `−32.7%` vs JSON but `+1.6%` vs JSON compact; semi-uniform event logs `+19.9%` vs JSON compact (https://github.com/toon-format/toon/blob/main/packages/toon/README.md).
- TOON benchmark methodology (https://github.com/toon-format/toon/blob/main/benchmarks/README.md): token counts via `gpt-tokenizer` (`o200k_base` encoding) across TOON/JSON/XML/YAML/CSV; accuracy = 244 questions over 13 datasets (8 primary + 5 structural-validation) on 4 models, deterministic type-aware answer validation, no LLM judge. Raw results: https://github.com/toon-format/toon/blob/main/benchmarks/results/token-efficiency.md (mixed-structure total TOON 264,734 vs JSON 393,637 vs JSON compact 260,451; employee records −60.7% vs JSON) and https://github.com/toon-format/toon/blob/main/benchmarks/results/retrieval-accuracy.md.
- Anthropic official docs (https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview, "Pricing"): cost = total input tokens including the `tools` parameter, plus `tool_use` and `tool_result` blocks; lists fixed per-model tool-use system prompt token counts (e.g. Claude Opus 4.6: 497 for `auto`/`none`, 589 for `any`/`tool`). No per-byte token formula.
- OpenAI official docs (https://platform.openai.com/docs/guides/function-calling, "Token Usage"): "functions are injected into the system message… callable function definitions count against the model's context limit and are billed as input tokens." Tool call output "should typically be a string… The model will interpret that string as needed"; image/file output arrays allowed. No token-cost table for tool output formats.
- MCP defines no token accounting for tool results (https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2026-07-28/server/tools.mdx lines 502–507).
